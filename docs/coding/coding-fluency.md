# 把写代码练得自然

写得自然，并不是不思考。常见结构不再占满注意力，你才能把精力留给新需求。你能很快知道该保存什么状态，下一步改变什么，哪里可能失败。

看答案时认得每行代码，只能说明你认得它。关闭答案后能构造、测试和修改，才算真正会写。

## 每次只练一个具体行为

今天的任务不要写成“学习异步”。换成一个小需求。搜索框连续输入 A、B，即使 A 晚返回，列表仍显示 B。卸载后不得更新。

这个目标让你知道何时完成。它也能解释每个变量为什么存在。

| 需求里的词 | 代码要保存什么 | 容易遗漏的反例 |
| --- | --- | --- |
| 最新 | 请求代次或身份 | 旧请求最后完成 |
| 最多两个 | 运行计数和等待队列 | 抛错后没有归还名额 |
| 只执行一次 | 执行前改变的状态 | 执行期间重入 |
| 可以取消 | 信号和等待者 | 等待阶段取消后仍启动 |
| 重启后保留 | 持久记录和恢复位置 | 内存数据随进程退出丢失 |

从[异步题解](workshop-web-async.md)选一道。先写输入和预期结果。不会选择数据结构时，先画三个事件，不要急着找模板。

## 先追踪，不复制

把五个事件写成表。先手算，再看实现。

| 事件 | 当前代次 | 能否写回 |
| --- | --- | --- |
| 发出 A | 1 | 尚无结果 |
| 发出 B | 2 | 尚无结果 |
| B 成功 | 2 | 可以 |
| A 成功 | 2 | 不可以，A 保存的是 1 |
| 卸载 | 3 | 之前所有请求都不可以 |

“当前身份”和“发出时身份”必须是两份值。如果两个回调都只读取最新身份，你就无法判断它们属于哪次请求。

下面只是解释时序的片段。两个业务函数由应用提供，完整实现和测试在[请求题解](workshop-web-async.md)。

```js
let generation = 0;
async function search(query) {
  const mine = ++generation; // 发出时保存身份，完成时才能识别旧请求。
  const result = await fetchResults(query);
  if (mine !== generation) return; // 取消网络不保证旧回调不会完成。
  renderResults(result);
}
function dispose() {
  generation++; // 让所有在途请求失效。
}
```

先保存身份。接着等待响应。最后检查自己是否还属于最新请求。三步都来自需求，不是凭记忆拼代码。

再问一个问题。如果 B 失败，A 成功，可不可以显示 A？这里规定不可以。A 不代表最新输入。如果产品要求保留最近成功结果，就要增加独立的成功状态。

## 逐步撤去提示

第一遍读带注释实现。每读一行，都问删掉它会破坏哪个测试。

第二遍只看函数签名、输入输出和测试名。遮住身份比较和清理步骤，自己补全。

第三遍打开空白文件。不看源码，完成同样的行为。

卡在 `mine` 时，不要先找答案。先说出完成时需要知道自己属于哪次请求，再把这个关系写成变量。API 拼写可以查文档。状态关系需要自己追踪。

| 卡在哪里 | 当次做什么 | 复盘记什么 |
| --- | --- | --- |
| 不知道从哪开始 | 写一个最小输入输出例子 | 需求没拆清楚 |
| 状态互相矛盾 | 列状态和允许的转移 | 状态模型不完整 |
| 错误后卡住 | 追踪一次拒绝、取消或重入 | 失败路径漏了 |
| 测试偶尔失败 | 记录事件顺序，减少真实时间依赖 | 验证不可重复 |
| 换题面就不会 | 用同机制写另一种业务 | 迁移练习不够 |

## 改需求，让旧答案失败

把 `search` 改名为 `loadProducts` 不算变式。下面每项都会改变代码。

1. 最新请求失败，保留上一份成功结果，但仍不能让过期回调写回。
2. 相同查询合并请求，不同查询各自保存身份。
3. 一个订阅者取消，不能取消其他订阅者共享的请求。
4. 保存操作可能已经写入服务器，超时不能直接再写一次。
5. 卸载后还要关闭读流、Worker 或观察器。

先新增测试。确认旧实现失败，再改代码。这样才会练到不同问题。[业务状态题解](workshop-web-business.md)和[Node 服务韧性](workshop-node-service-resilience.md)可以接着做。

## 换一种语言，再解释一次

| 机制 | 浏览器 JavaScript | Node.js | Go |
| --- | --- | --- | --- |
| 等待工作 | Promise 和任务队列 | Worker 池消息队列 | channel 和 goroutine |
| 取消 | AbortSignal 和代次 | 请求销毁和线程终止 | context 和取消分支 |
| 下游太慢 | ReadableStream 和帧预算 | write 返回值和 drain | 有界 channel 和阻塞发送 |
| 清理 | 移除监听和观察器 | close、destroy、terminate | defer、关闭所有者、WaitGroup |

不要逐字翻译。Promise 并发不等于 CPU 并行。Go channel 也不是任何接收者都能随意关闭。

从[真线程池](workshop-node-workers-streams.md)练到[Go 并发](workshop-go-concurrency.md)。每次写清楚谁创建资源，谁结束工作，谁等待完成。

## 一次练习，留下什么

| 时间 | 工作 | 留下的成果 |
| --- | --- | --- |
| 0–5 分钟 | 写一个正常、一个失败例子 | 两个可判定结果 |
| 5–12 分钟 | 手算事件，选择状态 | 状态表和函数签名 |
| 12–30 分钟 | 独立实现，运行测试 | 可以执行的模块 |
| 30–40 分钟 | 加一个需求变式 | 能击败旧代码的新测试 |
| 40–45 分钟 | 复盘最难的一步 | 原因、修复和下一次练习 |

当天练完，不代表长期掌握。可以从次日、三天后、一周后的复习安排开始。这是练习建议，不是证明过的最优间隔。

复习时先不看答案，直接写或解释失败用例。连续两次独立通过后换场景。持续卡住，就缩小问题，不要只扩大题量。

## 怎样知道自己进步了

记录题号、提示次数、独立写出时间、遗漏的失败路径。一周后再试一次。不要只记录刷了多少题，也不要用敲键盘速度判断水平。

能先说出输入输出。能不看答案写出完整实现。能解释关键状态和清理步骤。需求改变后，能新增测试并改代码。四件事都做到，再把题标为掌握。

## 自测

<details><summary>会背 LazyMan，却不会写上传队列，少练了什么？</summary>

少了迁移练习。上传还需要并发名额、进度、失败和取消。先选一个新约束，写一个串行 LazyMan 不能通过的测试。接着分别练[链式调用](workshop-web-javascript.md)与[上传存储](workshop-node-upload-storage.md)。

</details>

<details><summary>看完整答案仍不理解，应该继续硬刷吗？</summary>

先检查前置知识。把输入缩小到两个事件或两个元素。追踪一轮状态，解释一个判断，再增加需求。不能手算最小例子时，不要把复制答案当作完成。

</details>
