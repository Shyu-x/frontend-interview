# Day 6：文件记忆，以及 Skills 与 Todo 的职责边界

## 学习目标

- 解释记忆为什么要带 key、来源和更新时间，并支持按 key 更新。
- 区分持久记忆、可按需加载的操作技能、当前任务待办。
- 能指出伴随项目今天真正实现了什么，以及哪些只是架构概念。

## 前置与项目位置

- 前置：完成 Day 4，理解持久化；会使用 Node 文件 API 和 Promise。
- 环境：Node.js 22.18 或更高版本。
- 项目：`examples/minicode/`
- 阅读：`src/memory.ts`、`tests/session-security.test.ts` 中 `FileMemory` 用例。

## 运行

```bash
cd examples/minicode
npm run typecheck
npm test
```

## 观察行为

`MemoryRecord` 保存 `key`、`value`、`source` 和 `updatedAt`。`upsert()` 找到相同 key 时覆盖原记录，否则追加；`search()` 对 key/value 做不区分大小写的子串查找。现有测试验证同一 key 被用户更正后，新值和来源会保留。

可用这个区分来设计更大的 Agent：记忆回答“以后还要记住什么”，技能回答“遇到某类工作该按什么流程做”，todo 回答“这一次运行接下来要完成哪一步”。后两者不是 `FileMemory` 已实现的功能，本课不假装它们已经接入 Agent loop。

## 源码走读：用户更正缩进习惯

已有测试先写入 `{ key: "style", value: "tabs", source: "user" }`，再写同 key 的 `spaces`，来源改为 `user-correction`（实际记录还包含合法的 `updatedAt`）。

1. `upsert()` 验证四个字段，复制输入，避免调用者之后修改对象影响排队写入。
2. 当前实例的 `#pending` 把写操作串行连接；第二次操作要等第一次完成，才能读到最新文件。
3. 第一次 `list()` 遇到文件不存在时返回空数组；写入后数组有一条。第二次找到相同 key，替换该项，不追加副本。
4. 更新内容先写到同目录唯一临时文件，再 `rename` 替换目标。若写临时文件失败，不会直接把已有目标截成半个 JSON。
5. `search("spaces")` 对 key/value 做大小写不敏感的子串匹配，返回新值和新来源。它没有按 source、时间或语义相似度排序。

这条走读证明“用户修正可以覆盖旧事实”，不证明系统自动知道哪条事实更可信。相同 key 的更新策略仍是最后一次写入胜出。

## 三种状态不要混成一个 memory.json

| 状态 | 回答的问题 | 生命周期 | 典型例子 |
|---|---|---|---|
| 记忆 | 以后还要记住什么？ | 跨会话，需更正/删除/过期 | 用户明确偏好、项目约束 |
| 技能 | 某类任务应如何处理？ | 按需发现和加载 | 发版步骤、代码审查流程 |
| Todo | 本次工作进行到哪里？ | 当前任务，需状态迁移 | 待开始、运行中、失败、完成 |

把 Todo 写成长期事实，会使下一次会话继续执行已经过期的步骤。把整个技能库塞进每轮上下文，会增加成本并稀释当前约束。记忆同样不应该默默升级权限：一条“用户以前批准过 shell”的记录，不能代替本次执行授权。

## 持久化取舍与失败

JSON 文件方便人工检查和小规模恢复，但每次更新都要读整个数组。文件较大或多进程共用时，应考虑数据库、事务或明确的单写入服务，而不是只增加一个内存 Promise 队列。

`rename` 使本次替换避免直接覆盖到半途；同实例队列避免两个更新基于同一旧快照互相覆盖。但两个 `FileMemory` 实例分别持有自己的队列，仍可能发生最后写入覆盖。没有 fsync、数据库事务或备份，也不能承诺断电后持久化。

加载合法 JSON 后还要检查记录结构；损坏文件不能被悄悄当成空记忆覆盖。若记忆来源是网页或工具输出，它仍是不可信数据，不能作为系统指令执行。生产实现需要来源、权限、保留期和注入防护。

## 实战任务

在 `tests/session-security.test.ts` 为 `FileMemory` 增加用例：写入两个不同 key 的记录，用大小写不同的关键词搜索，确认只返回匹配项；再次 upsert 其中一个 key，确认记录数不增加。

**通过标准：**`npm test` 通过；搜索不区分大小写；重复 key 更新原记录而非新增副本；返回记录仍包含来源和更新时间。

## 故障练习

临时删除 `upsert()` 中“找到已有 key 时替换”的分支，运行记忆测试。观察重复记录如何出现，并思考之后 `search()` 应返回哪一个版本。恢复实现。

## 验收与面试提问

- 验收：能解释记忆记录四个字段的作用，并用一次用户更正说明来源追踪价值。
- 面试：什么信息适合写入长期记忆？如何过期、删除或纠正旧记忆？为什么技能正文不应每轮都塞进上下文？todo 状态如何表示失败或阻塞？

## 边界

当前实现有同实例串行队列和临时文件加 rename 替换，没有跨实例/跨进程锁、冲突解决、权限审批、fsync 或语义检索。`search()` 是字面子串匹配，不是向量搜索。Skills 和 Todo 只有设计讨论，没有对应运行模块。
