# MiniCode：七天构建可验证的 Agent 教学骨架

本课程不是七组互不兼容的代码片段。你始终在同一个 TypeScript 工程中学习：先理解模型响应，再接上工具闭环，然后增加会话、权限、记忆和子任务。每一步既要能解释机制，也要能证明失败时仍有可预测的行为。

伴随项目是 **离线教学骨架**：模型由 FakeModel 驱动，工具示例是加法，没有真实模型供应商适配器，也没有执行任意 shell 或自动编辑仓库的编码能力。完成课程可以理解编码 Agent 的工程边界，但不能据此宣称交付了生产级 Claude Code。

## 先运行，再阅读

前置：掌握 JavaScript 的对象、数组、Promise、异常，能阅读 TypeScript 接口和联合类型。文件系统、HTTP 与 AbortSignal 不熟悉时，可先读对应知识点，再做当日实验。

需要 Node.js **22.18+**。这是直接运行可擦除 TypeScript 语法的项目，不需要先编译输出；类型检查仍然必须单独运行。

从仓库根目录：

```bash
cd examples/minicode
npm ci
npm run verify
npm run demo
```

`verify` 先做严格类型检查，再执行 Node 自动测试。成功标准是所有测试通过，而不是命令没有打印异常。`demo` 的最后一行应为：

```text
2 + 3 = 5
```

测试默认离线，不要求 API Key；不要为运行课程提交密钥。源码入口见 [伴随工程 README](https://github.com/Shyu-x/frontend-interview/tree/main/examples/minicode)。

## 第一次运行到底发生了什么

把 demo 的输出和 `src/demo.ts`、`src/agent.ts` 并排看：

1. 用户输入先写入历史。第一次模型响应不是答案，而是一条 `add` 工具调用，参数是 `{ a: 2, b: 3 }`。
2. assistant 消息保留工具请求及 ID。注册表检查工具存在、参数有效、授权通过，才执行工具。
3. 结果不是直接返回给用户，而是写入 `role: "tool"` 的 observation，关联同一个调用 ID。
4. 第二次模型请求携带这条 observation。FakeModel 返回最终文本，不再要求工具。
5. loop 根据“没有工具调用”结束，返回 `reason: "final"`，并发出运行结束事件。

因此，Agent 的核心不是“模型能调函数”一句话，而是 **决策、执行、观察、继续或停止** 组成的受控闭环。FakeModel 让这条轨迹固定下来，便于定位工程错误；它不能证明真实模型会选择正确工具。

不要按“文章数量”记录进度。每天提交的学习产物应包含：运行命令、观察到的状态变化、一条失败用例、设计取舍说明。

### 每阶段的验收门槛

| 阶段 | 不看文章也必须做到 | 对应失败实验 |
|---|---|---|
| Day 1–2 | 画出输入、适配器、消息历史、运行结果之间的关系 | 耗尽 FakeModel 响应队列，区分工程异常与模型最终答案 |
| Day 3 | 按调用 ID 找到工具请求和结果，说明何时停止 | 非法参数、未知工具、token 或工具预算耗尽 |
| Day 4 | 区分事实日志与派生摘要，不拆开工具调用轮次 | 中间日志损坏必须报错；未完成尾行可恢复 |
| Day 5 | 说明注册表授权点和路径检查为何不同 | 越界路径、符号链接、用户拒绝和策略 deny |
| Day 6 | 更正事实后保留新的来源，不覆盖无关记录 | 同实例并发写入；损坏记忆结构 |
| Day 7 | 区分调度结束、worker 终止和副作用撤销 | 预取消、非合作 worker 超时、父子目录冲突、低报用量 |

具体断言位于 `tests/agent.test.ts`、`session-security.test.ts`、`subagents.test.ts`、`regressions.test.ts` 和 `boundaries.test.ts`。测试名描述它证明的行为；阅读测试比只看“pass”更重要。

## 能力递增，不是组件堆砌

Day 3 到 Day 7 的每个模块都在解决前一步暴露的工程问题：

- loop 能继续调用模型，但历史变长，因此 Day 4 区分可恢复日志与有限上下文；
- 日志能保存行为，但不能阻止危险行为，因此 Day 5 在执行前加入授权和路径边界；
- 完整历史不适合直接当长期知识，因此 Day 6 保存带来源的事实并允许纠正；
- 单个上下文不一定适合独立审查任务，因此 Day 7 用显式合同拆分，而不是复制全部聊天历史。

只有出现相应问题，才引入新能力。例如能用目录检索解决的任务，不应仅为展示技术而引入向量数据库；单 Agent 已足够的任务，也不必启用多 Agent。

## 前端工程师的加练

读 [Agent 前端运行面板](../agent/architecture/frontend-agent-ui.md)，把 `src/ui-state.ts` 接到自己熟悉的组件框架：

1. 用 `runId` 隔离两次运行，用 `sequence` 处理重放和事件缺口。
2. 按 `callId` 渲染工具卡，按 `requestId` 渲染审批卡。
3. 取消按钮先显示“取消请求中”，等待后端终态；不要把浏览器断开当作工具已终止。
4. 用文本节点渲染模型输出，不直接插入未受信 HTML。
5. 使用 `tests/ui-state.test.ts` 的事件序列复现重复、迟到、缺口和重复审批。

现有项目只交付框架无关 reducer 与测试，没有组件页面、SSE 服务端、持久事件流或恢复接口。以上是你的扩展任务，不是仓库已提供的 UI 产品。

## 什么已经实现，什么仍是设计练习

| 能力 | 当前状态 | 不能作出的承诺 |
|---|---|---|
| 模型调用 | FakeModel 与适配契约 | 已验证真实供应商协议或模型推理质量 |
| 权限 | 显式拒绝、审批钩子和路径检查 | 具有 OS 沙箱；绝无符号链接竞态 |
| 会话 | JSONL、事件结构校验、截断尾行恢复 | 多进程写入事务或不可丢失的事件流 |
| 压缩 | 有长度上限的历史摘录、保留完整 user 轮次 | 语义摘要正确、约束永不丢失、token 永不超限 |
| 记忆 | 同实例串行更新、临时文件加 rename | 跨实例/跨进程锁、断电持久性或访问控制 |
| 子任务 | 函数 worker、合同/结果校验、并发和预算计量 | 独立模型进程、持久后台队列、自动重试或强制杀 worker |
| 前端状态 | 纯 reducer、身份关联、重放/缺口测试 | 服务端审批验证、实际断线恢复或完整 XSS 防护 |

“没有实现”并不是遗漏的文案问题：这些能力需要单独的威胁模型、接口和实验。先把边界说清，再决定是否值得扩展。

## 面试训练

30 秒回答：Agent Loop 让模型提出工具请求，由工程代码校验、授权和执行，把结果回灌，再根据停止条件继续或结束。模型决定下一步，但宿主负责副作用边界、预算和可观察性。

2 分钟追问：用 demo 解释一次成功，再选择一个失败测试，说明失败进入 observation 还是终止运行；最后解释取消只能停止等待/传播信号，不能保证撤销外部副作用。

给自己的回答打分（共 10 分）：

- 闭环与调用 ID 配对：2 分。
- 错误处理与三个独立预算：2 分。
- 权限和取消的边界：2 分。
- 会话/记忆/摘要的区别：2 分。
- 能引用测试，而非自报“做过 Agent”：2 分。
